# Sessions and host operations

CLI, ACP, SDK and dashboard conversations share Raw's session store. Visible history is an ordered record for readers; model context is the current input used for inference. Reading history, renaming a conversation or inspecting metrics does not attach a runtime, claim a writer or renew retention.

The dashboard accepts turns and manual compaction with a client request ID. Acceptance is durable before the response. Repeating that ID with the same submitted intent returns the existing operation, even after completion or restart. Reusing it for different input is a conflict. One session has one writer through startup, execution and cleanup; other sessions may run independently.

An operation progresses from `accepted` through `starting` and `running` or `compacting`, then ends as `completed`, `max_steps`, `cancelled` or `error`. An abandoned operation whose owner is demonstrably gone becomes `interrupted`. It is never automatically resubmitted. The first user message and consumption of the accepted input commit atomically. Tools that may have executed before a crash retain `outcome_unknown`; inspect their effects before requesting another action.

## Turns the CLI takes

A turn that Claude Code starts on its own after a background command, or that Raw sends to Codex with the note of a finished command, is an operation of the session like any other: a `turn` with `origin: "cli"` and the note as its input. It holds the session's lease, streams live, can be stopped (Stop also stops Claude Code's turn in the CLI), and its history shows the notice "<CLI> continues: <note>" in place of a user message. It starts at once on an idle session, after the running operation otherwise (an interrupting message still goes first, queued messages after it). When another process holds the session, Claude Code's turn is stopped and Codex's note waits for this process's next turn, each with a notice. If the turn cannot start, Claude Code's turn is stopped and what it said is kept as a notice.

## Messages sent while a turn runs

The dashboard can send a message while one of its turns runs in the session. The message waits in the session's queue (at most 20 messages that are waiting, being delivered, paused or blocked). A message sent to an idle session starts a turn as before.

- **Delivery points.** A running turn takes queued messages only where its next step is a model request: after the turn's own message (for messages queued while it started), after all tool results of a step, and after the output-limit notice that continues a cut answer. Each waiting message is delivered, oldest first, as its own user message in the model context and a `user` history record with `queued: true` and the turn's `operationId`. Panel-action notes travel with it as with any user message. A pending approval or question is never answered by the queue; the message waits for the end of that step.
- **Hooks.** Each delivered message goes through `UserPromptSubmit`. A message a hook refuses is `blocked` with the hook's reason and is not delivered; the turn continues with the next message.
- **At most once.** Taking a message marks it `delivering`; the user message and the receipt `delivered` (with the operation and the history sequence of its record) commit in one transaction. A Stop during delivery puts the message back. Deleting a message the agent already took answers `already_sent`.
- **End of a turn.** When a turn completes with messages left, the oldest becomes the next turn (its request ID, text, attachments and request override) in one transaction that ends the previous operation and moves the session's lease to the new one without releasing it; another process cannot claim the session in between. The rest are delivered at that turn's first delivery point. Stop, an error, `max_steps` or an interrupted turn pauses every waiting message instead; nothing starts until you send again. If the next turn cannot start, the previous turn still ends and the message is paused with the reason. After a restart, messages of an interrupted turn are paused.
- **Interrupt and send.** A message sent with `mode: "interrupt"` (or a waiting, paused or blocked message sent with Send now) stops the running turn the way Stop does and starts the next turn with that message, through the same hand-off: the lease is never released in between. What the turn finished stays: completed tool results, and the cancelled result of a call that was running (a Bash process is terminated as on Stop). What it had not finished is dropped: a partial answer is not in the next request, and a pending approval or question is settled `cancelled`. Messages queued before the interrupt are not paused; they are delivered in the new turn after its own message. Of two interrupts in a row, the newer one starts the turn and the earlier one becomes an ordinary queued message delivered after it. On an idle session an interrupt is an ordinary send, and Send now starts the message as a turn.
- **Receipts.** A message keeps its request ID for the session's lifetime. Once delivered, started as a turn or deleted, only the receipt stays (state, operation, history sequence); its text and attachment bytes are released, since the model context holds its own copy. Attachment bytes of a waiting message are stored with it (large values in payload files), so they survive a restart.

Each turn attaches the selected current agent/config and closes its runtime afterward. An agent on Claude Code or Codex whose CLI still has background work keeps its adapter after the turn, for the session's next operation only; a changed agent, a deleted session or the dashboard stopping stops it and its tasks, with a notice on the next turn ([backends](backends.md#background-work)). An idle browser does not prevent CLI resume. Changed configuration follows the ordinary runtime reconciliation rules; unchanged turns preserve the request prefix. Closing a tab only detaches its view. Stopping an operation aborts its runtime and pending approvals.

Compaction replaces older model context with a checkpoint and keeps the newest steps verbatim ([context](context.md)). With `compact.strategy: "native"` the provider's own compaction item is stored at the start of the context and sent unchanged after restart; another provider gets readable text in its place: the summary for Anthropic, or the earlier written checkpoint with a note for an encrypted OpenAI item. The user's messages and `ask_user` answers that leave the active context are stored in the session's compaction ledger with the observed working-state facts, so they survive restart and later compactions; `/clear` deletes the ledger with the history. A session compacted by an earlier release has no ledger: Raw rebuilds it from the stored history when the original request matches exactly one history row, and otherwise keeps the original request and notes that earlier messages are unavailable. Successful replacement and its visible summary marker commit together; earlier visible history is retained. Manual and automatic attempts expose the same identity and outcomes: `compacted`, `noop`, `not_smaller`, `cancelled` or an error. A failed automatic attempt is a warning: the turn continues with a fallback and its operation can still end `completed`; only a manual compaction ends its operation with the error. Byte counts describe serialized context; token counts are explicitly estimates. Loaded skill content removed by compaction keeps the existing reload notice. Compact can affect upstream cache reuse without changing the session ID.

History projections accept existing CLI and ACP envelopes. They preserve record order, tool linkage and available statuses, and label abbreviated previews. Historical output, image bytes, detailed timing or full write diffs may be unavailable; reading current files is not a reconstruction of historical results. No history read executes a tool.

Tool views ([panels design](panels-design.md)) use static chat/sidebar placement. Sidebar panels retain their latest session document and a small `panel_receipt` per committed update. Chat views retain a distinct immutable snapshot per call in `session_tool_views`; the receipt references its host-owned instance ID. Both are committed atomically with the tool result. Reading them needs no runtime, claim or model credential. History pages contain references rather than all documents; `GET /api/sessions/:id/views/:instanceId` fetches one inline snapshot. Chat views do not count against the 16 sidebar panels and never create empty sidebar sections. Deleting/expiring the session cascades its snapshots. Compaction retains display history and views, while reminders use only open sidebar summaries.

Operation receipts and metrics are optional host records in the same format-5 database, cascade-deleted with their session. They are never injected into the model prompt. An unrelated unsupported legacy database remains isolated by the existing store-location policy.

## User message blocks

A stored user message is text or an ordered list of `text`, `resource_link` and `image` blocks. Image bytes stay inside the saved message (large values use the existing payload files); history views, terminal history, titles and compaction summaries show `[Image: type, N bytes]` instead of base64, while ACP replay forwards the stored image block. Switching between vision and non-vision agents never rewrites the saved image; see `docs/providers.md` for request-time placeholders.

Managed background jobs keep session ownership independently of the model-turn lease. Foreign deletion fails while their supervisor is alive; expiry defers these sessions. Owner-host deletion fences new starts and stops jobs before deleting records. A failed cleanup retains the session. See [process lifetime and recovery](processes.md).

The library `deleteSession` API returns a Promise in all cases. Await it, and supply `processes` when this host owns a persistent supervisor so deletion can await cleanup. That supervisor's store is authoritative; combining it with `storeOptions` is rejected. A supervisor without a store cannot delete saved sessions. The store's direct synchronous deletion remains guarded and cannot remove live process ownership.
